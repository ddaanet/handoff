# Changelog

One entry per design change, newest first. Each links the full write-time
record under `changelog/` — what the defect was, what was weighed, what was
believed at the time. Those files are never edited after the fact; a change
that reverses one heads the affected section with a superseding pointer.

[`design.md`](design.md) is the other half: present tense, current truth,
rewritten rather than annotated when a decision is reversed.

- [2026-09-17 — Memory moves inside the deciding step](changelog/2026-09-17-memory-moves-inside-the-deciding-step.md) — `handoff`'s protocol opened with "make zero tool calls before invoking `handoff-checkpoint`" and then put memory writes in a step between the two deciding ones, so following the steps broke the rule and honouring the rule left memory nowhere to go before the checkpoint that keys on it; the two deciding steps collapse into one with memory inside it, before the checkpoint and after the commit answer that sets its tense, and the prohibition names memory writes as its one exception; a commit the ask implies moves from before the checkpoint to after it, where it carries the staged handoff files and still precedes arming, in both skills
- [2026-09-14 — A heading is not a leading `#`](changelog/2026-09-14-a-heading-is-not-a-leading-hash.md) — `is_empty_body`, FR6's whole definition of empty and the one rule `checkpoint.py` and `write-stage.sh` share, was wrong in both directions: `line == ""` is not blank, so `"task": "   "` wrote a three-byte file that passed `handoff_frame`'s byte-length gate and was injected as a frame carrying nothing, while `startswith("#")` is not "is a heading", so a body of `#!/bin/sh` or `#tag` was judged empty and the file *removed* — the asymmetry that matters, one injecting a frame that says nothing and the other deleting one that said something; the rule is now markdown's own ATX heading against the line with trailing whitespace gone, and the leading-space bound is the part worth stating, since stripping each line closes both routes as filed and re-opens the second one indent along, a four-space code block's `# comment` being content exactly as a shebang is
- [2026-09-14 — The vocabulary is closed at both levels](changelog/2026-09-14-the-vocabulary-is-closed-at-both-levels.md) — `checkpoint.py` rejected an unrecognized key inside an action object but not in the payload that holds them, so a superfluous top-level key — `tasks` beside a well-formed `task` and `todo` — was discarded without a word, while a *misspelled required* key still failed loudly, both keys being required by key presence; `validate_top_level_keys` now names any key outside the union any skill takes, flat rather than skill-dependent because every known key under a skill that forbids it is already rejected upstream by name, and a per-skill check has no later point to hook than ahead of those five, where it would win and replace `forbidden when skill is "autoname"` with a generic `unknown key` — adding precision that has no case left to apply to at the cost of the wording that says which mistake was made; it runs before either half is applied, pinned by a row whose task half would clear a pre-existing frame
- [2026-09-13 — The named path is the report](changelog/2026-09-13-the-named-path-is-the-report.md) — `bash-post.sh` claimed "git's stderr now reaches the user", which nothing demonstrated and a probe against CC 2.1.270 disproves: a hook's stderr on `exit 0` lands on a `hook_success` transcript attachment carrying no `rendered` field, echoed to no one and injected into nothing, so the path named on both channels is not a convenience beside git's own explanation but the entire report; two changes follow from that, since the agent-facing sentence named a path and attached no act to it although the manifest is consumed either way and nothing downstream stages these gitignored paths — it now ends `— stage with git add -f before the next commit`, and the user-facing summary deliberately does not — and a handoff root that is no git repository, which is the environment rather than a defect, was discovered once per manifest line and reported in the wording reserved for breakage, so `git rev-parse --git-dir` now separates that whole-run case ahead of the loop and reports it once
- [2026-09-13 — Nothing is written until both halves resolve](changelog/2026-09-13-nothing-is-written-until-both-halves-resolve.md) — `main()` applied the task half and then the todo half, so a wrap-up whose todo `edit` named an `old_string` that matched nothing — the ordinary boundary where the task finished and the list has leftovers — removed `handoff-task.md`, wrote no manifest, staged nothing, and reported an error naming only `todo.old_string`, with nothing on either channel connecting the two; hoisting the two `edit` checks ahead of the task half removes today's triggers and leaves the ordering unchanged, so the next apply-time failure anyone adds reopens the defect silently, and writing the manifest for whatever was applied records a loss the user has to notice first and cannot recover at all when the frame never reached a commit — so each half now resolves to a `FilePlan` carrying the path, the act, the body and its manifest lines, every `err()` the wrap-up's write path raises happens while resolving, and only once both plans exist does anything touch the disk; with the edited body in hand at plan time the emptiness test reads a value on both halves, so an empty body is never written first on either
- [2026-09-07 — The payload names its actions](changelog/2026-09-07-the-payload-names-its-actions.md) — a session that finished publishing a release wrote `"task": null` meaning "nothing more to say", the checkpoint read it as "do not touch the file", and the next session loaded a stale frame calling the release unpublished; `null` had been given that no-op meaning deliberately three months earlier, which put one spelling in front of two fields whose correct behaviours are opposite — a no-op is right for the scratch list (FR4) and preserves a finished frame as current for the task file; `task`/`todo` become a tagged union naming each action, both keys required by key presence so `null` and an absent key are each a named error, `file_path` goes since the path was composed from `HANDOFF_ROOT` anyway, and removal becomes unlink-if-present so a `D` manifest line records only a removal that happened
- [2026-08-15 — The continuation waits for the composer to exist](changelog/2026-08-15-continuation-waits-for-the-composer-to-exist.md) — the first end-to-end dogfood against the real product landed `/exit` and the relaunch, but the continuation line typed into a boot screen with no composer yet: measured at 3.9s for a bare launch of this exact plugin/hook chain to render one, against a fixed ~3.5s budget (`wait_for_idle`'s near-instant resolution plus a 3s landing poll) sized for driving a TUI that is already running, which holds for `/compact`/`/clear`'s continuations but not `restart`'s, the one case `SessionStart(resume)` fires at the very start of a fresh process's boot; `wait_for_composer` now polls for the glyph's mere presence before `_drive_line`'s existing sequence runs, a no-op mid-session where the composer is already there
- [2026-08-14 — The relaunch stops replaying argv](changelog/2026-08-14-the-relaunch-stops-replaying-argv.md) — the first unattended driven restart came up with every launcher flag doubled: the morning's probe had established only that the CLI *parses* duplicates, not that they compound, and since the replayed argv is the argv the shims produced, each restart hands them a line they inject into again — unbounded growth; every flag replay was carrying came from a shim that resupplies it on re-entry (plus `GITLORE_LAUNCHED`, which no argv could carry), so the line is now typed exactly as the checkpoint composed it and the whole parent-chain walk goes with the replay — `handoff_resume_command`, `handoff_claude_pid`, the `/proc` readers, the fake-process-tree seam and eight bats rows — leaving a hand-typed flag on a shim-less install as the accepted, silent loss
- [2026-08-14 — The relaunch presses Enter once](changelog/2026-08-14-relaunch-presses-once.md) — three driven restarts left the relaunch typed at the shell prompt and never submitted, with no offline reproduction across six probes (idle fish, busy fish, the shell path standalone, the full `/exit`-then-relaunch against a real TUI) and the flush-on-terminal-reinit mechanism ruled out; resending Enter through the poll fixed it and was itself worse — the signal being retried against is the resumed session's `SessionStart`, a whole boot away, so every retry was guaranteed to press into a starting session where a stray Enter answers a dialog rather than costing an empty prompt line; the losses stopped anyway once argv replay went and the line shrank to `claude --resume <sid>`, so delivery and confirmation are now separate questions the way only a shell line allows — Enter repeats while `pane_foreground` still reads as the shell, and the sentinel is waited for without touching the pane
- [2026-08-14 — The relaunch is typed by name, so it re-enters the shims](changelog/2026-08-14-relaunch-through-the-shim.md) — the same restart came up with `GITLORE_LAUNCHED` unset and auto-memory outside the submodule: replaying argv[0] names the real binary, walking past both shims on PATH (`--plugin-dir <root>`, gitlore's `--settings '{"autoMemoryDirectory":…}'`), and walking further up the parent chain cannot reach them because a shim `exec`s — same pid, no entry, argv[0] substituted; argv replay could not have fixed it in any case, since gitlore's shim also exports `GITLORE_LAUNCHED=1`, which is on no command line and which its own anti-double-inject guard reads, so re-running the launcher is the only thing that restores it — slot 0 alone is rewritten to the bare `claude` and the shell resolves it as the user's own invocation did, keeping the replayed flags (a shim re-injects an identical duplicate, which the CLI accepts) rather than dropping them and losing a hand-typed flag on an install with no shim to resupply it
- [2026-08-14 — The relaunch line is dispatched by its command, not a prefix](changelog/2026-08-14-resume-line-dispatch.md) — the second driven `restart` typed its relaunch line into the shell and never Entered it: `main` dispatched the shell path on `line.startswith("claude --resume ")`, but `stop-drive.sh` rewrites that slot to the exiting process's own argv, whose argv[0] is the resolved binary — so the line fell through to `_drive_line`, which typed it and then waited for a `❯` composer that had exited, taking the previous day's foreground gate down with it by never reaching the branch; every fixture at both ends spelled argv[0] as the bare word `claude`, which is 2026-08-13's assert-the-premise defect one layer up, so recognition becomes `shlex.split` + argv[0] basename + `--resume` among the arguments (the real line begins with `/`, so the leading-character rule reads it as a slash command), and a producer-side bats row pins an absolute argv[0] against a mutation of the basename match
- [2026-08-13 — Restart drive repair](changelog/2026-08-13-restart-drive-repair.md) — the first driven `restart` relaunched the *hook wrapper's* argv with `--resume` appended, carrying an unexpanded `${CLAUDE_PLUGIN_ROOT}` a fresh login shell resolved to nothing, and typed it into a terminal Claude Code had not released yet: both failures are one root — nothing identified the `claude` process — so `handoff_resume_command` now walks the parent chain by argv[0] basename (`$PPID` is the `/bin/sh -c` wrapper Claude Code spawns, at a depth the shell's exec-optimisation decides) and the relaunch gates on `#{pane_current_command}` reverting rather than on a fixed settle; the single-file test seam that had substituted for the exact expression under test becomes a fake process *tree*, and the tmux premise the new gate rests on is pinned against a live TUI rather than the stub that was asserting it
